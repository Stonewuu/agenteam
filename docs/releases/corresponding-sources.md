# 保存与成品对应的第三方源码

成品镜像除了本项目代码，还包含基础系统、语言运行环境和原生库。同一个镜像标签在不同日期构建时可能取得不同版本，只保存项目的依赖清单或上游主分支链接，无法确定交付时使用的源码。每次正式发布都应按实际成品核对所需源码、原补丁、构建说明和第三方条款，并随版本保存这些资料。

## 从实际成品定位

先按[第三方声明资料](third-party.md)采集实际镜像和应用依赖。系统包使用实际记录中的源码包名称和完整版本，包括发行版追加的版本后缀；不能只使用上游主版本号。单独复制进镜像的 Java、Node、Python、Docker 客户端和图片处理库需要另外定位，不在系统包清单中的程序也要核对。

`scripts/release/locate-system-source-packages.py` 按 `runtime-sources.json`（实际镜像的系统来源记录）查询指定发行版的 `Sources.xz` 或 `Sources.gz`（源码包索引）。例如：

```sh
python scripts/release/locate-system-source-packages.py \
  --runtime-report 实际镜像目录/runtime-sources.json \
  --index https://deb.debian.org/debian/dists/bookworm/main/source/Sources.xz \
  --index https://security.debian.org/debian-security/dists/bookworm-security/main/source/Sources.xz \
  --output 新的源码定位目录
```

发行版和版本根据实际报告选择，上例不适用于所有镜像。工具记录精确匹配结果、源码文件地址、文件大小及 SHA-256（内容摘要）；未匹配的版本保留在 `missing` 中，不自动改成最新版。结果只说明已定位文件，尚未下载源码。索引原文也会保留，应使用发行版提供的公钥验证 `InRelease`（带数字签名的仓库内容清单），再核对其中的索引摘要。

当前仓库移除了旧版本时，继续在对应发行版的官方历史归档中寻找。历史归档的保留期限不能当作本项目长期提供源码的承诺；正式需要交付的资料应保存原文件。

## 保存源码和构建修改

`scripts/release/fetch-source-archives.py --manifest <文件清单.json> --output <新目录>` 下载已核对的源码及补丁。文件清单的 `files` 数组包含 `file`（文件名）、`url`（采用加密网络传输协议的原始 HTTPS 下载地址）、`type`（tar 表示源码归档，text 表示文本，patch 表示补丁）和可选的 `sha256`（上游发布的摘要）。只有上游确实提供摘要时才填写；工具不会把首次下载得到的摘要称为上游验证。

对于不能直接解析格式的压缩补丁或原始签名文件，可以使用 `binary`（按原始字节保存），但必须同时提供上游摘要；不能仅根据 `.asc` 后缀推断签名一定是文本。`bytes`（上游文件大小）存在时也会逐项核对。默认逐个下载，单文件上限为 256 MiB（每单位 1048576 字节）；可以用 `--workers 4` 同时读取最多四个文件，使用 `--max-file-mib 512` 明确提高大源码文件的上限。提高前先核对正式清单中的大小和本机可用空间。

工具保留原文件、清单和逐项结果，不解压或执行源码，不覆盖已有目录。下载失败、摘要不同或归档不可解析时保留未完成状态；`complete` 只表示本清单下载完成，不表示范围和许可已经全部核对。

源码必须同时包含相应的构建修改。例如，图片库的上游构建脚本可能应用补丁、修改配置、静态合并其他库，或调整 Rust（原生程序开发语言）依赖。应保存对应提交的完整构建脚本、补丁原文及依赖版本记录；不能只保存顶层源码包，也不能把构建脚本的许可套给其构建的所有程序。

`scripts/release/collect-source-notices.py` 可以读取一个或多个已完成的 `--download-report <download-results.json>`，用 `--output <新报告.json>` 保存归档内原声明。工具重新核对每个归档摘要，不解压文件；编译类或同名源代码文件不会被误当作许可原文。缺少独立声明的 Rust 源码包保留原始 Cargo.toml，并单独列出，不补写猜测的署名。报告可通过声明生成工具的 `--source-notice-report` 参数加入第三方材料，索引会明确这些条目来自附送源码，包含构建、测试和其他平台内容。

系统源码包中的 `.dsc`（源码文件和摘要描述）、原始源码归档及发行版补丁应保持文件名和关联关系。一份原始源码同时服务多个系统包时可以共用，但每个镜像与源码版本的关系仍须保留。

## 与版本一起交付

需要提供的第三方源码整理为独立附件，与对应发布的镜像编号、声明索引和文件摘要关联。在线交付时从该版本的下载说明提供明确入口；离线交付时同时提供源码附件和说明，客户不需要访问维护者工作目录。多个成品共用同一份源码附件时，应列出其适用镜像和组件。

`scripts/release/create-source-archives.py --manifest <附件清单.json> --source-root <原材料目录> --output <新目录>` 用于生成附件。清单中的每一组列出目标文件名、原材料内部路径、原地址、大小和摘要；工具不扫描并整包复制工作区。生成后逐个读回附件中的文件，验证没有遗漏、额外文件或内容变化。输出索引保留公开来源信息，省略本机原材料路径；只有所有分组都完成时，结果才记录 `complete=true`（全部附件封装完成），许可和正式发布状态继续单独核对。

第三方源码和声明继续适用它们各自的许可。源码附件不应混入客户信息、签发密钥或无关的私有项目代码。发布前核对具体条款和实际文件范围；下载成功的条目数不能代替这项核对。
